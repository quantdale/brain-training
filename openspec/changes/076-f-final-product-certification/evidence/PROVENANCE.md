# Evidence provenance — 076-f terminal certification

**Change:** `076-f-final-product-certification`
**Task:** 1.2 — game/route provenance table
**Companion:** [`SOURCE_EQUIVALENCE.md`](SOURCE_EQUIVALENCE.md) (task 1.3)
**Rows:** [`provenance-table.md`](provenance-table.md) / [`provenance-table.json`](provenance-table.json)
**Identity:** [`TERMINAL_IDENTITY.json`](TERMINAL_IDENTITY.json)

## Why this file exists

Campaign 076 failed once on exactly this point: historical screenshots were
being read as proof about an APK that did not produce them. The rule this file
enforces is the one in the change spec:

> A frame SHALL NOT be labeled as a capture from an APK that did not produce it.

So every frame used for acceptance carries a provenance record with a source
commit, an APK identity, its production dependency, its capture identity, its
visual-review status, its current applicability, and whether recapture is
required.

## The rows are derived, not transcribed

`provenance-table.md` is generated by
`node scripts/certification/build-provenance.mjs` directly from the committed
capture manifests and from the single
[`TERMINAL_IDENTITY.json`](TERMINAL_IDENTITY.json):

| Source | What it supplies |
| --- | --- |
| `…/076-product-wide-ui-ux-reboot/evidence/final-matrix-de6c5fcd/captures.json` | 90 route pairs (3 profiles × 2 themes × 15 surfaces) |
| `…/evidence/final-scroll-de6c5fcd/captures.json` | 2 Results-scroll reachability pairs |
| `…/evidence/after-captures-games/index.json` | 194 retained + 16 quarantined game frames |
| `evidence/TERMINAL_IDENTITY.json` | the terminal source SHA and APK SHA-256 — read by this generator **and** by `build-assessment.mjs`, so the identity is stated once |

The generator recomputes the dependency-surface diff with `git diff` and
**fails closed**: it exits non-zero while the surface is dirty, it never emits
`SOURCE_EQUIVALENT_HISTORICAL` for a row whose *rendered* closure changed, and a
changed file with **no recorded effect** disqualifies every historical row
outright. Re-run it after any source change.

Totals: **302 rows** — 90 route, 2 route-scroll, 194 game, 16 rejected.
`rows currentApplicability=true: **0**`.

## Classification vocabulary

Four classes. The fourth was added by the 2026-10-09 reconciliation because the
previous three could not express "the closure changed, so this still is no
longer a picture of its surface":

| Class | Meaning |
| --- | --- |
| `CURRENT_APK` | The frame was produced by the terminal APK itself. |
| `SOURCE_EQUIVALENT_HISTORICAL` | Produced by an earlier build whose **rendered** dependency closure is unchanged since capture. **Not** a terminal-APK capture — comparison evidence only. |
| `SOURCE_NOT_EQUIVALENT` | Produced by an earlier build whose **rendered** dependency closure **changed** since capture. Neither a terminal-APK capture nor a faithful picture of the surface. Recapture required. |
| `NOT_APPLICABLE` | Quarantined/rejected capture, retained for audit and never used for acceptance. |

Two per-row booleans carry the rest, and they answer **different** questions:

| Field | Question it answers |
| --- | --- |
| `currentApplicability` | Can this row serve as current terminal-APK acceptance evidence? True only when the frame's own APK hash equals the terminal APK hash. |
| `recaptureRequired` | Must this frame be recaptured (or the row marked NOT VALIDATED)? True when the frame's rendered closure changed. |

A row can be a faithful picture (`SOURCE_EQUIVALENT_HISTORICAL`) and still be
unusable as terminal-APK evidence (`currentApplicability: false`). That
combination is exactly the 90 route rows, and conflating the two is how the
earlier ledger went wrong.

`interactionClosureChanged` records the third dimension: a change that affects
only input handling leaves stills valid but invalidates every interaction claim
drawn from them. It is `true` for all 92 route rows (the 4 dp hit slop) and all
194 game rows.

## How each evidence family is classified

### Route matrix (90 pairs) and scroll pairs (2) — `SOURCE_EQUIVALENT_HISTORICAL`, `currentApplicability: false`

Every row binds to `de6c5fcd…` / `c324960…` in the manifest itself: `apkSha256`,
`codeSha`, `pngSha256`, `xmlSha256`, `windowsXmlSha256`, `visualReview`,
`captureIssues`, `routeVerified`, `foregroundVerified`, `blank`. They were
captured from a real APK and reviewed as six labelled contact sheets, and their
own rendered closure is unchanged — but that APK is not the terminal APK, so
**none of them is a terminal-APK capture.**

### Game frames (194 retained) — `SOURCE_NOT_EQUIVALENT`, `recaptureRequired: true`

- **22 closure frames** carry a real per-file APK binding to `b2913bca…` at
  source `4a6fc53…`.
- **172 earlier frames** are mixed-build captures with no per-file APK binding,
  individually state-verified in the earlier audit.

**None is a terminal-APK capture, and none is source-equivalent any more.** The
generator writes `SOURCE_NOT_EQUIVALENT` for all of them and records the source
as `mixed historical builds (no per-file binding)` where no binding exists,
rather than inventing one.

### Quarantined frames (16) — `NOT_APPLICABLE`

Retained in `after-captures-games/rejected/` with explicit reasons. Never used
for acceptance.

## Current-device rows are separate again

The per-game rows under [`current-device/`](current-device/) are the
*current-device acceptance checks*, and they are a different evidence family
from the historical frames above. A historical frame is never promoted into a
current-device row. The APK those rows were graded on is recorded in
[`assessment.json`](assessment.json) as the `apk` field, derived from the rows'
own `APK under test:` line and reported beside `terminalApk` — never in place of
it.

## What this file does not claim

- It does not certify any game. `assessment.json` reads **42 NOT VALIDATED**.
- It does not make the historical frames terminal-APK captures.
- It does not assert release acceptance. Provenance is a precondition for
  acceptance, not acceptance.
- It does not claim the 90/90 route matrix is terminal-APK proof.
