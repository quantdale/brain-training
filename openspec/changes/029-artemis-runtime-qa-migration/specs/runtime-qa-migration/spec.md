## ADDED Requirements

### Requirement: Android runtime QA uses the external ARTEMIS boundary

The repository MUST document Google ARTEMIS at `D:\Tools\artemis` as the
authoritative Android runtime/device-QA controller. ARTEMIS MUST NOT be copied
or vendored into the repository, and current runtime documentation MUST NOT
present a custom gameplay driver as authoritative.

#### Scenario: Repository-side QA checks run without the driver

- GIVEN a clean product checkout without the external ARTEMIS directory
- WHEN the repository runtime-QA contract, CI, or Android setup self-test runs
- THEN it validates the documented ARTEMIS handoff and does not invoke a
  repository gameplay driver

### Requirement: Provider credentials remain outside the product repository

Provider credentials MUST remain in the external ARTEMIS environment or an
existing host environment variable. They MUST NOT be printed, committed,
placed in Codex configuration, or written to repository logs, traces,
screenshots, task text, or durable state.

#### Scenario: Configuration is inspected after MCP integration

- GIVEN the ARTEMIS MCP server has been generated and merged into Codex
- WHEN the repository and user configuration are inspected
- THEN only non-secret command, working-directory, and runtime environment
  settings are present in the MCP block and the provider credential remains
  external

### Requirement: Observable app seams remain available to ARTEMIS

The migration MUST preserve stable semantic IDs/accessibility labels, the
`braintraining://` deep-link scheme, deterministic fixtures/seeds, versioned
game/scoring/generator metadata, structured diagnostics, and safe
development-only QA controls needed for reproducible ARTEMIS tasks.

#### Scenario: Offline contract checks the app observability seams

- GIVEN the current mobile app source and configuration
- WHEN the offline runtime-QA contract runs
- THEN it finds the deep-link scheme and semantic-ID seam while the existing
  deterministic fixtures, metadata, diagnostics, and development-only hooks
  remain available to the app

### Requirement: Repository runtime checks stay deterministic and offline

The repository MUST provide an offline runtime-QA contract check that does not
require provider credentials, an emulator, Metro, or network access. CI,
certification, and Android setup self-tests MUST use this contract rather than
invoking the removed gameplay driver.

#### Scenario: Contract validation runs with runtime dependencies absent

- GIVEN no emulator, Metro server, provider credential, or network connection
- WHEN `node scripts/qa/validate-runtime-qa-contract.mjs` runs
- THEN it completes using repository files only and reports the contract
  result deterministically

### Requirement: Only the requested ARTEMIS MCP integration is installed

The Codex MCP configuration MUST be generated by the supported ARTEMIS path
and merged as the ARTEMIS server block while preserving unrelated user
settings. The migration MUST NOT run the broad `mcp --install all` command or
overwrite global agent rules. An already-running Codex process MAY require a
restart, and that state MUST be reported honestly.

#### Scenario: ARTEMIS MCP merge preserves existing servers

- GIVEN a Codex configuration containing unrelated MCP servers
- WHEN the supported ARTEMIS generator and merge path is used
- THEN the ARTEMIS server is present, unrelated servers remain unchanged, and
  the need to restart an already-running Codex process is recorded if present

### Requirement: Live runtime evidence is classified from actual outcomes

Each Flash or Pro task MUST be reported as `PASS`, `FAIL`, `BLOCKED`, or
`NOT VALIDATED` from its actual task/trace result. Model 503/429/404 responses,
missing credentials, unavailable devices, and interrupted tasks MUST NOT be
reported as product passes. External traces MUST remain outside Git unless a
safe, credential-free summary is needed in durable validation.

#### Scenario: Provider unavailability blocks a task honestly

- GIVEN an ARTEMIS task reaches the device but its configured model is
  unavailable or quota-limited
- WHEN the task result and trace are reconciled
- THEN the task is recorded as `BLOCKED` or `NOT VALIDATED` with non-secret
  evidence, and no product runtime pass is claimed
