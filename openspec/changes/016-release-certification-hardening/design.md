# Design — Campaign 016 Release Certification & Hardening

## 1. Campaign ordering

016 MUST remain PROPOSED while 015 is machine-readable ACTIVE.

Phase 0 closes 015 first. Only after `GOVERNANCE.activeCampaign`, `STATE`, `CURRENT_CAMPAIGN`, `EXECUTION_PROMPT`, task ownership, and OpenSpec lifecycle agree that 015 is closed may 016 be activated atomically.

This preserves the repository invariant of exactly one top-level active campaign
while work is executable. Once 016 is validated and no successor is authorized,
the explicit terminal state is `GOVERNANCE.activeCampaign: null` with
`lastCampaign` and `lastCampaignStatus: VALIDATED`; the campaign identity and
status in STATE, CURRENT_CAMPAIGN, EXECUTION_PROMPT, OpenSpec, and task
ownership remain synchronized. This prevents an unavailable external device
from keeping a completed campaign ACTIVE forever without pretending that
manual/device evidence passed.

## 2. Hardening philosophy

This campaign is evidence-first:
- no game #43;
- no speculative architecture rewrite;
- no store/monetization/cloud expansion;
- no blanket dependency churn;
- no performance rewrite without measured evidence;
- no conversion of unavailable validation into PASS.

P0/P1 findings block progression. P2/P3 findings may be fixed when low-risk and evidence-backed or recorded as non-blocking debt.

## 3. Release-certification layers

### Layer A — repository truth
Lifecycle state, task status, generated artifacts, lockfiles, CI definitions, docs, and exact-SHA evidence must agree.

### Layer B — clean checkout
A clean clone must install with `npm ci` and reproduce registry/provenance/offline/governance checks, typecheck, lint, full Jest, web export, Expo Doctor, and native prebuild/build smoke where supported.

### Layer C — Android runtime
Use only the dedicated brain-training device. Repair the emulator/runtime environment through a bounded compatibility matrix rather than blind retries. Once stable, run fresh post-015 journeys, then one complete certification pass.

### Layer D — iOS compile compatibility
Use a macOS GitHub runner for a no-signing simulator build smoke. Generate native iOS state from committed Expo config, install pods, and run an Xcode simulator build with signing disabled. This is compile evidence, not device UX certification.

### Layer E — runtime resilience
Exercise persistence corruption boundaries, duplicate/idempotent completion routing, process death/relaunch, storage unavailable, backup/restore rollback, app background/pause/resume, and failure-path observability.

### Layer F — CI signal integrity
A green build must make warnings and skips interpretable. Expected failure-path logging should be asserted/suppressed inside tests, skipped tests should match a small explicit allowlist, and new skips/unexpected console output should fail the classification gate.

## 4. Android emulator recovery strategy

The current blocker is host/emulator infrastructure, not a proven product failure. Use a bounded matrix:
1. capture current SDK/emulator/Hyper-V/WHPX/graphics/AVD configuration;
2. reproduce the segfault once with full emulator/ADB logs;
3. test one known-stable emulator version or pinned SDK toolchain;
4. test a software-rendering/headless-safe profile;
5. test a fresh dedicated AVD generated from committed script inputs;
6. if still unstable, test a physical Android device through ADB if one is available without host-input automation.

Do not loop indefinitely. If the bounded matrix fails, preserve evidence and mark runtime gate BLOCKED, not PASS.

## 5. iOS build-smoke design

Add a separate macOS workflow/job that:
- checks out the repo;
- installs Node and dependencies with `npm ci`;
- runs repo validators and TypeScript before native generation;
- runs `npx expo prebuild --platform ios --clean`;
- installs CocoaPods dependencies as required;
- discovers the generated workspace/scheme deterministically;
- runs `xcodebuild` for an iOS Simulator target with `CODE_SIGNING_ALLOWED=NO`;
- archives concise build logs on failure.

No App Store signing, provisioning, TestFlight, or release listing work is introduced.

## 6. Test-signal design

The current CI has 4 skipped suites / 5 skipped tests and expected `console.error` output.

Implement:
- an explicit skip allowlist with exact file/test names and rationale;
- a CI parser/gate that fails on any new skip outside the allowlist;
- a dedicated opt-in performance command/job for performance suites when appropriate;
- local spies/mocks for expected `console.error` in failure-path tests so unexpected console errors remain visible;
- a concise machine-readable Jest summary artifact.

## 7. Security/privacy boundary

Because the app is offline-first and has no production auth/backend, security hardening focuses on:
- permissions generated by Expo prebuild;
- no accidental network dependency/runtime call;
- backup/import integrity and path/size validation;
- secret/config leakage;
- unsafe debug/QA hooks in production builds;
- dependency audit classification, separating runtime from build/dev-only advisories.

Do not claim external-service security that does not exist in current scope.

## 8. Performance boundary

Use the existing probe suite. The current evidence includes:
- `loadProgressSnapshot_20000` around 141 ms;
- backup/export work materially slower than ordinary queries (multi-second in the 5k-session synthetic probe).

Profile only if the same workload reproduces a user-relevant bottleneck. Optimize only with before/after evidence and preserve format compatibility.

## 9. Final certification artifact

The terminal checkpoint must include:
- exact start/final SHAs;
- exact workflow run IDs;
- clean-checkout command matrix;
- Android device/runtime evidence;
- iOS build-smoke evidence;
- Jest pass/skip/warning classification;
- dependency/security classification;
- performance evidence;
- remaining debt with severity;
- explicit statement that deferred product areas remain intentionally out of scope.
