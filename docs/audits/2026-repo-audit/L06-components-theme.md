### L06-F02 — `Tappable` silently discards its merged `accessibilityState` (spread order)
- Severity: P2
- Confidence: confirmed
- Category: api-contract
- Files: `apps/mobile/src/components/ui/tappable.tsx:95` (computed merge), `apps/mobile/src/components/ui/tappable.tsx:106` (`{...rest}` spread)
- Evidence:
  ```tsx
  // tappable.tsx
  accessibilityState={{ disabled: disabled === true, ...(rest.accessibilityState ?? {}) }}   // :95
  hitSlop={resolvedHitSlop}
  onPressIn={…} onPressOut={…}
  style={[style, pressed && pressedStyle, animatedStyle]}
  {...rest}>                                                                                  // :106
  ```
  `accessibilityState` is **not** destructured out of props, so it is still present in `rest`; JSX applies props left-to-right, so the raw caller value overwrites the merged value on the line above. Callers that pass a partial state therefore lose the `disabled` flag: `components/ui/segmented-control.tsx:117` (`accessibilityState={{ selected }}`), and any `Card`/`Chip`-style caller that supplies its own state. `components/ui/chip.tsx:81` happens to re-state `disabled` itself, and `ui/button.tsx:151` computes `{ disabled: inactive, busy: loading, … }` and passes the whole object down, so those two paths are unaffected — which is why the defect is invisible in existing tests.
- Problem: the primitive's own disabled-announcement contract is dead code for every caller that supplies `accessibilityState`; the merge line only takes effect when the caller supplies nothing at all.
- Why it matters: a disabled-but-selected segmented option is announced to TalkBack as "selected" with no disabled state, so a screen-reader user is told a locked control is available; the same shape is copied by any future composite widget. The site deliberately asserts disabled-ness (`disabled={…}` on `Tappable` in `ui/button.tsx`, `settings/confirm-button.tsx`), so the intended semantics and the rendered semantics disagree.
- Root cause: prop-order bug — the "spread the rest" idiom placed after computed accessibility props, combined with not destructuring `accessibilityState`.
- Recommended solution: destructure `accessibilityState` in the parameter list and omit it from `rest`, then spread `rest` *before* the computed `accessibilityState`, e.g. `{...rest} accessibilityState={{ disabled: disabled === true, ...accessibilityState }}`. Keep the `Omit<PressableProps, …>` type as-is.
- Implementation considerations: after the fix, `Chip`/`Button`/`GameButton` values must be re-checked for duplicate keys (`button.tsx:151` already merges `disabled`/`busy` itself — the merge is idempotent). The same idiom appears elsewhere in shared components (`game-button.tsx:83` passes a fresh object into `Button`; `Card` passes through to `Tappable`), so audit those two call sites in the same change. Preserve `disabled === true` strictness so an explicit `disabled={false}` never overrides an inherited `true` unless the caller says so.
- Dependencies: a11y lane (screen-reader contract tests), games lane (difficulty selector / segmented chips).
- Risks: changing effective accessibility state could alter existing rendered-tree assertions in `components/game-ui/__tests__/*.a11y.test.tsx`; expect and justify such diffs rather than reverting the fix.
- Validation required: a focused unit test rendering `Tappable` with `disabled` **and** `accessibilityState={{ selected: true }}` and asserting the queried node's `accessibilityState` contains both `disabled: true` and `selected: true`; run `npx jest apps/mobile/src/components/ui apps/mobile/src/components/game-ui apps/mobile/src/components/shell`.
- Completion criteria: the merged object is the value actually applied to `AnimatedPressable`; a regression test fails if the spread order is restored.

### L06-F03 — `memo` is effectively absent from the kit; `GameButton`'s memo is inert at ~42 % of its call sites
- Severity: P2
- Confidence: confirmed
- Category: performance
- Files: `apps/mobile/src/components/game-ui/game-button.tsx:56` (`export const GameButton = memo(...)`), `:83` (`accessibilityState={{ disabled, selected }}`), `:86` (`style={[...]}` new array per render), `apps/mobile/src/components/ui/button.tsx:145-186` (unmemoised `Button`), `apps/mobile/src/components/ui/tappable.tsx` (unmemoised `Tappable`), `apps/mobile/src/components/themed-text.tsx:80` (unmemoised `ThemedText`)
- Evidence: only **three** components in the whole kit are wrapped in `memo` — `grep -rn "React.memo\|memo(" apps/mobile/src/components` → `discovery/game-card.tsx:104` (dead code), `discovery/game-poster-tile.tsx:37`, `game-ui/game-button.tsx:56`. The two most-used primitives are not memoised: `ThemedText` (160 product importers) and `GameButton`'s entire downstream chain (`Button` → `Tappable` → `AnimatedPressable`). `GameButton`'s memo cannot fire for most game call sites: `grep -rn "onPress={() =>" apps/mobile/src/games` → **119** inline arrow handlers against **286** `<GameButton` JSX uses, and the same call sites pass fresh `style={[…]}`/`hint`/callback identities each render. `GameButton` itself also builds new `accessibilityState={{ disabled, selected }}` and `style={[small ? styles.buttonSmall : styles.button, style]}` objects every render, so even stable callers pay a new-props cost at the `Button` boundary.
- Problem: a re-render of any game screen (which happens on every stimulus/trial change) re-renders its whole button row, every label and every `Tappable`, with no memo barrier; the one memo that exists is defeated by inline props in ~2 of 5 uses.
- Why it matters: 42 game screens use this kit in their hottest loop. Each trial typically re-renders a screen whose subtree includes several `GameButton`+`ThemedText`+`Tappable` instances; without memo barriers the work is proportional to the number of controls rather than to the number that actually changed, which is exactly the class of jank that shows up as dropped frames on low-end Android during timed games (speed/attention domains). Note: this audit is static — no frame data was captured, so the *magnitude* is unmeasured.
- Root cause: memoisation was never applied as a kit-wide policy; the single `memo` on `GameButton` was added without stabilising the props it compares.
- Recommended solution: (1) memoise the leaf primitives that are render-cheap and prop-stable — `ThemedText`, `Tappable`, `Button`, `IconButton`, `Card`, `Chip`, `GameButton` — and hoist every render-body object/array (`accessibilityState`, `style={[…]}`, variant colour maps) into module scope or `useMemo` within those components; (2) at the call sites, either pass stable handlers (`useCallback`, or move the handler into `GameButton` via a `payload` prop) or accept that memo cannot fire and instead memoise the row components in the games lane. Prefer fixing the primitives first: they are shared, so the win multiplies without touching 286 call sites.
- Implementation considerations: `Button` is a `forwardRef` component — wrap in `React.memo(forwardRef(...))` and keep the `ref` prop signature intact (React 19 ref-as-prop is used by `GameButton`). Memoising `Tappable` interacts with L06-F02 (fix the spread order first, then memoise, otherwise the broke state becomes cached). Do not memoise components that receive children-heavy `ReactNode` props from inline JSX expecting re-render (`Card`, `EmptyState` children change every parent render anyway) without measuring.
- Dependencies: L06-F02 (must land first), games lane (call-site handler stability), perf/observability lane if it captures frame data.
- Risks: memoising a component whose props include non-primitive defaults (e.g. `Skeleton`'s `width = '100%'`, `Tappable`'s `pressedStyle` objects) can freeze updates if the comparator is wrong; use the default shallow comparator and verify with the existing kit suites rather than a custom one.
- Validation required: `npx jest apps/mobile/src/components` (no behavioural diff), plus a render-count assertion (a `<GameButton>` row rendered twice with identical props must render the leaf once) in a new focused test. If a frame-level claim is made, it needs the runtime lane (`ARTEMIS`) — see "Not covered".
- Completion criteria: (a) every leaf kit primitive that renders no state of its own is `memo`-wrapped; (b) no kit component allocates a new object/array literal for a prop that memo would compare; (c) a render-count test proves the barrier exists for `GameButton`+`ThemedText`.

### L06-F04 — Theme and sensory settings share one context, so a SFX toggle re-renders every themed component
- Severity: P3
- Confidence: strongly indicated
- Category: performance
- Files: `apps/mobile/src/components/settings/settings-provider.tsx:84-87` (context value), `apps/mobile/src/hooks/use-theme.ts:16` (`useOptionalSettings()?.themeId`)
- Evidence:
  ```tsx
  const value = useMemo(() => ({ settings, setSetting, themeId, setThemeId }), [settings, setSetting, themeId]); // settings-provider.tsx:84
  …
  const themeId = useOptionalSettings()?.themeId ?? DEFAULT_THEME_ID;                                            // use-theme.ts:16
  ```
  `settings` is a dep of the memoised context value, so toggling SFX/haptics creates a new value object; every `useTheme()` consumer (i.e. essentially the whole UI: `ThemedText` alone has 160 importers) subscribes to that same context and re-renders even though `themeId` did not change.
- Problem: `useTheme` needs exactly one field of a four-field context, but reads the whole context, coupling palette consumers to sensory-preference churn.
- Why it matters: toggling a switch in Profile (or any future settings write) invalidates every visible themed component in the tree — the same class of work as a palette change, for a value no themed component reads. It costs frames on a screen the user is actively toggling, and it is the kind of coupling that later makes `useTheme` unusable in memoised leaves (a memoised `ThemedText` would still re-render, because context changes bypass `memo`).
- Root cause: two concerns (visual theme, sensory preferences) were folded into one provider/context rather than two selectors.
- Recommended solution: split the context into `SettingsContext` (sfx/haptics) and `ThemeContext` (themeId/setThemeId), keeping `SettingsProvider` as the composition root that renders both providers. Keep `useTheme()`'s tolerant `useOptionalSettings` fallback semantics (many tests and previews render without a provider).
- Implementation considerations: the tolerant-read contract must survive the split for both hooks (`useOptionalThemeId` returning `undefined` outside a provider). `settings-provider.test.tsx` and the `theme-resolution.test.tsx` hook suite assert the current shape — update them deliberately, not by loosening assertions. `onSettingsChange` persistence semantics are unaffected.
- Dependencies: settings/theme lane, testing lane (hook suites).
- Risks: splitting providers can change render order effects during bootstrap (`app/_layout.tsx` mounts `SettingsProvider` + `AudioHapticsProvider`); keep the nesting order identical to today's to avoid changing initial paint.
- Validation required: `npx jest apps/mobile/src/components/settings apps/mobile/src/hooks`; plus a focused test asserting a `useTheme()` consumer does **not** re-render when only `setSetting('sfx', …)` is called (render-count spy).
- Completion criteria: sensory-setting updates do not re-render theme-only consumers; existing persistence and startup behaviour unchanged.

### L06-F12 — Toast visibility is a fixed 2.8 s with no user control, and overflow silently drops the oldest message
- Severity: P3
- Confidence: confirmed
- Category: frontend
- Files: `apps/mobile/src/components/ui/toast.tsx:66` (`TOAST_VISIBLE_MS = Motion.celebration * 4` → 2800 ms), `:43-49` (`MAX_QUEUED_TOASTS = 8` at `:43`, `toastQueue.shift()` on overflow at `:48`), `:98-104` (single timer, one toast at a time)
