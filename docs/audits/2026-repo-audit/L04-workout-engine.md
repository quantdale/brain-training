## Flow map
1. **Create.** `Home` -> `useWorkout({domainRatings, recentGameIds, balance})` -> `db.workouts.reconcile(date, eligibleGameIds())`; if unrepairable/none -> `personalizedWorkout(eligibleGames(), date, …)` (`WORKOUT_SIZE = 4`, `today.ts:23`) -> `orderDailyBySignals`/`explainSignalOrder` (`v3.ts`) -> `db.workouts.getOrCreate(date, {gameIds, seedVersion}, metadata)`. Templates: `useWorkoutTemplates().startTemplate` -> `selectTemplateWorkout` (count = `gameCountForLength`, 2/4/6) -> `getOrCreate(<date>::<template>::<length>)`.
2. **Launch a leg.** `Home` `gameHref(game.id, {instanceKey, legIndex: index, gameId})` (`(tabs)/index.tsx:869`) / results-screen `gameHref(nextGameId, nextProvenance)` (`results.tsx:504`) -> `/game/[id]?workoutKey&workoutIndex` -> `parseWorkoutLaunchProvenance` (`game/[id].tsx:71`, envelope-validated) -> `WorkoutSessionLaunchProvider` -> `useGameSession.begin()` -> `registerWorkoutSessionLaunch(sessionId, workoutLaunch)` (`use-game-session.ts:169`) -> in-memory `pendingLaunches` map (`session-provenance.ts:36`).
3. **Complete + decorate.** game screen -> `completeSession` (`db/sessions.ts:323`) -> `launchProvenance = explicitProvenance ?? peekWorkoutSessionLaunch(id)` (`:379`) -> `attachWorkoutProvenance(rawResult, …)` -> durable `game_sessions` row carries `workoutProvenance`; `clearWorkoutSessionLaunch` after commit (`:566`). `INSERT OR IGNORE` + `isNew` gates ledger/rating (`:452`-`:470`).
4. **Advance a leg.** Two callers, one implementation: `game-host/results.tsx:232` (in-game chrome, after `persistState === 'succeeded'`, guarded by `advancedLaunchRef` keyed `${instanceKey}:${legIndex}`) and `use-workout-result-advance.ts:111` (the `/results` route, guarded by `advancedForSessionRef` keyed `session.id`), both -> `advanceWorkoutForSession` (`session-advance.ts:90`) -> `shouldAdvanceWorkout` (`advance.ts:29`, exact `(key, legIndex, gameId)` + `instance.gameIds[legIndex] === gameId` + `status === 'active'`) -> `db.workouts.advanceForSession` (`db/workout.ts:712`) -> conditional UPDATE (`status='active' AND current_index=? AND updated_at=? AND reroll_attempt=? AND seed_version=? AND game_ids_json=?`) -> `nextIndex = min(currentIndex+1, len)`, `status = nextIndex >= len ? 'completed' : 'active'`. Non-owning callers instead read + `reconcile` (persisted repair) and navigate from the true current leg (`session-advance.ts:53-127`).
5. **Reroll.** `useWorkout.reroll` (`use-workout.ts:186`) -> refuse if not `active` or `rerollAttempt >= MAX_REROLLS_PER_DAY` (5) -> `nextWorkoutAfterReroll(…, exclude = played prefix)` -> positional merge `[...prefix, ...freshIds]` -> free: `db.workouts.applyReroll`; paid: `paidReroll(db, {cost, operationId: \`workout-reroll:${date}:${nextAttempt}\`, mutateWorkout})` (ledger dedupe + debit + CAS write in one transaction) -> `WorkoutWriteConflictError` -> `refresh()` + rethrow.
6. **Reconcile (catalog drift).** Pure `reconcileWorkout(instance, eligibleIds)` (`reconcile.ts:62`) — played prefix verbatim, future legs filtered/deduped, retired future legs substituted from pool order to preserve length, `completed` rows byte-identical (index clamped only), `null` => regenerate. Persisted via `WorkoutRepository.reconcile` -> `observeRepair`/`applyRepair`/`persistRepaired` with a CAS on `(current_index, status, game_ids_json bytes)`.

## Findings

### L04-F01 — A completed leg is not advanced durably; nothing reconciles "session persisted, leg not advanced" (in-memory provenance bridge + one-shot ref-guarded advance)
- Severity: P2
- Confidence: confirmed (code gap: in-memory bridge, ref-guarded one-shot advance, no recovery scan); the exact kill window is statically established but the runtime timing is `requires runtime validation`
- Category: reliability | data-integrity
- Files: `apps/mobile/src/workout/session-provenance.ts:36` (`pendingLaunches`), `apps/mobile/src/components/game-host/use-game-session.ts:169` (`registerWorkoutSessionLaunch`), `apps/mobile/src/db/sessions.ts:379` (`peekWorkoutSessionLaunch`) and `:566` (`clearWorkoutSessionLaunch`), `apps/mobile/src/components/game-host/results.tsx:220-232` (`advancedLaunchRef` + `advanceWorkoutForSession`), `apps/mobile/src/workout/use-workout-result-advance.ts:47-51` (`useDbData(..., [sessionId])`) and `:88` (`advancedForSessionRef`)
- Evidence:
  - `session-provenance.ts:36`: `const pendingLaunches = new Map<string, WorkoutSessionProvenance>();` — module comment: "The in-memory launch map bridges the route and the existing shared game persister without requiring every one of the 42 game modules to grow a new prop."
  - `use-game-session.ts:169`: `if (workoutLaunch?.gameId === gameId) { registerWorkoutSessionLaunch(sessionId, workoutLaunch); }` runs in `begin()` — i.e. **at session start**, before any gameplay.
  - `db/sessions.ts:379`: `const launchProvenance = explicitProvenance ?? peekWorkoutSessionLaunch(id);` — the durable row is decorated from that in-memory map at completion time.
  - `game-host/results.tsx:222-232`: advance runs only when `persistState === 'succeeded'`, keyed once by `advancedLaunchRef.current === launchKey` (`${instanceKey}:${legIndex}`); `advancedLaunchRef.current = null` only when `persistState` returns to `idle`/`started` (a replay). A failed advance therefore never retries for that session.
  - `use-workout-result-advance.ts:47-51`: the instance query dependencies are `[sessionId]` only — no focus/refresh key — and `:88` `if (advancedForSessionRef.current === session.id) return;` blocks the retry even though the surrounding `session` object identity changes on focus refetch.
  - Absence: `grep -rn "workouts\.advance(\|advanceForSession(\|advanceWorkoutForSession("` returns only `results.tsx:232`, `use-workout-result-advance.ts:111`, `session-advance.ts:124` — every caller is a mounted result surface for one session. No code path scans `game_sessions` for provenance-bearing sessions whose leg is still current (`findActiveInstanceForSession` is only ever called *with* a session in hand).
  - Contrast: `advance.test.ts:207` ("reopens persisted session ownership before advancing after process death") always performs `registerWorkoutSessionLaunch` → `completeSession` → `advanceForSession` in one process, so it does not cover the gap.
- Problem: the leg transition is a *second*, dependent write after `completeSession`. If it does not land, nothing re-derives it. Two concrete windows: (a) process force-stop / OOM between `begin()` and completion wipes `pendingLaunches`, so `completeSession` persists the session as **standalone** (`workoutProvenance` absent) — that session can never own the leg, by design (`isWorkoutSessionProvenance` gate); (b) the advance write fails or the app dies right after `completeSession` commits — the session *is* decorated durably (this is the happy path of `advance.test.ts:207`), but no surface ever re-attempts the advance because both guards are in-memory refs on the mounted screen.
- Why it matters: the user plays and saves a workout leg, and Home still shows the same leg as "Now" with the workout stuck at `currentIndex`. There is no operator/user signal (the only message is a one-shot toast "Workout progress could not be saved" on `/results`, `results.tsx:228-233`) and no durable retry; the user must replay the same game, and for window (a) the replay is the *only* recovery. Silent progress loss on the product's headline daily flow.
- Root cause: ownership is durable only at session-completion time (raw-result JSON), and the advance is a fire-and-forget effect guarded by component-local refs; the launch association itself is deliberately non-durable for the 40 games that have no workout awareness.
- Recommended solution: add a bounded, idempotent **advance-recovery pass** at Home/workout load (the same place `db.workouts.reconcileActiveInstances` already runs on the resume path): read recent sessions that carry `workoutProvenance` (one indexed query, e.g. `completed_at >= instance.createdAt`) and, for the live active instance whose `(date, currentIndex, gameIds[currentIndex])` matches the tuple, call the existing `advanceForSession` (it is already CAS-guarded, so a redundant call is a safe no-op and can never double-advance). Keep the in-memory bridge, but make it an optimisation rather than the only durable link — e.g. persist the launch tuple on the session row at `begin()` (new column or a reserved raw-result field written at start) so a kill mid-leg still records ownership.
- Implementation considerations: `advance` must stay exactly-once, so the recovery pass must reuse `advanceForSession`'s CAS rather than write directly; it must not resurrect a *past* leg (the guard already requires `legIndex === currentIndex`); the query must be bounded (`listActiveInstances(limit)` pattern) and must tolerate a missing/failing store by degrading to today's behaviour (no crash on Home load); do not add a second timer/poller — run it on the existing load/focus path; cross-day rows must stay untouched (yesterday's active row must not be advanced by today's session — `instanceKey` already carries the date, but a recovery pass must only consider the instance key it is loading).
- Dependencies: L01 (`db/workout.ts` persistence contract, `advanceForSession` CAS), session-persistence lane (`db/sessions.ts` decoration + `workoutProvenance` column/raw-result field), Home load path (`src/app/(tabs)/index.tsx`).
- Risks: an over-eager recovery pass could credit a leg the user never finished (only sessions with `workoutProvenance` are candidates, and only the exact current tuple advances); extra query cost on the Home critical path; a persisted launch tuple at `begin()` widens the raw-result contract and must be ignored by older readers (unknown keys degrade gracefully today, `parseWorkoutMetadata`-style validation applies only to metadata).
- Validation required: (1) unit/integration: new test in `apps/mobile/src/workout/__tests__/` that completes a session (provenance attached) *without* calling `advanceWorkoutForSession`, then runs the recovery pass on a fresh process/repository and asserts `currentIndex` advanced exactly once and a second pass is a no-op; (2) simulated-kill test: build the launch tuple, drop the in-memory map (`jest.resetModules()` or a fresh module registry) before `completeSession`, assert either the persisted tuple survives (fix b) or the documented standalone degradation is asserted explicitly; (3) runtime: complete a leg, `adb shell am force-stop <pkg>` from the results screen before the advance lands, relaunch, verify Home's "Now" marker and `workout_instances.current_index`.
- Completion criteria: after a kill/failure in the persist→advance window, relaunching Home shows the next leg as "Now" and `workout_instances.current_index` equals the number of legs actually played; `countCompleted` and the leg index are never double-incremented by the recovery pass; a standalone session still cannot claim a leg (existing `advance.test.ts:249` stays green).

### L04-F02 — Home lets a FUTURE leg ("Up next") be launched with its own `legIndex`, so the app hands out an ownership tuple that is false against the durable row
- Severity: P2
- Confidence: confirmed for the mislabelled launch tuple and progress copy; strongly indicated for the deferred auto-advance sub-case
- Category: correctness | frontend | api-contract
- Files: `apps/mobile/src/app/(tabs)/index.tsx:841-877` (row list + `gameHref` with `legIndex: index`), `apps/mobile/src/components/game-host/game-host.tsx:205` (`workoutPosition = workoutLaunch.legIndex + 1`), `apps/mobile/src/workout/advance.ts:44-50` (ownership predicate), `apps/mobile/src/workout/session-advance.ts:53-127`, `apps/mobile/src/workout/use-workout-result-advance.ts:60-71`
- Evidence:
  - `(tabs)/index.tsx:841`: `{workout.map((game, index) => {` … `:865` `isCompleted ? "done" : isCurrent ? "up now" : "up next"` … `:869-877`:
    ```
    onPress={() => router.push(gameHref(game.id, workoutFlow.instance ? {
        instanceKey: workoutFlow.instance.date, legIndex: index, gameId: game.id } : null))}
    ```
    Every row — including rows labelled "up next" — pushes a tuple whose `legIndex` is that row's position, with no `index === workoutIndex` guard.
  - `game-host.tsx:205`: `const workoutPosition = workoutLaunch?.gameId === gameId ? workoutLaunch.legIndex + 1 : null;` — the in-game chrome's "Game N of M" is computed from the route tuple, not from the durable row.
  - `advance.ts:44-50`: the completion-time guard requires `provenance.legIndex === instance.currentIndex && instance.gameIds[provenance.legIndex] === signal.gameId`, so an out-of-order launch **cannot** skip or double-advance a leg (fails safe); `session-advance.ts:53-59` then persists a `reconcile` repair and navigates from the true current leg. That rejection is unit-tested at the predicate level — `advance.test.ts:107-116` passes `legIndex: 1` with `gameId: "speed-tap-rush"` against `makeInstance()` (`currentIndex: 0`, `gameIds[1] === "speed-tap-rush"`) and expects `false`. What is *not* covered is the UI that emits such a tuple, and the deferred advance below.
  - Deferred advance: the `/results` route is reachable for any past session (`results.tsx:558` `href={\`/results?id=${s.id}\`}`), and `use-workout-result-advance.ts:64-71` fires `advanceWorkoutForSession` whenever `findActiveInstanceForSession` returns non-null — i.e. once the workout's `currentIndex` later reaches that out-of-order leg's index, merely *opening that old session's results page* advances the leg.
- Problem: the route can carry a launch tuple that does not describe the workout's current leg. Nothing validates the tuple against the durable row at launch (only at completion), so the UI can create a session whose "leg" is a position the workout does not own, and the in-game position copy states a leg identity that is untrue. Later, when the workout legitimately reaches that index, the older session silently owns that leg again and advances it from an unrelated screen (a `view` mutates progression state).
- Why it matters: (a) misleading progress copy in-game ("Game 3 of 4" while the workout is on leg 1) on a product that treats leg identity as source-of-truth evidence; (b) an out-of-order leg is credited by *viewing* history rather than by playing the current leg — the credit is for a game the user did play, so it is not false credit, but the state transition is triggered by navigation, is invisible, and is not what the ownership model claims ("Only a completed session that owns the current leg advances it" — the session owns the *index*, not the play event that the workout intended); (c) it makes the `legIndex` field ambiguous: "leg I was launched as" vs "leg I am".
- Root cause: `Home`'s leg list is a single tappable list for three distinct intents (replay a completed leg, resume the current leg, preview a future leg) and forwards `index` as the launch leg for all three.
- Recommended solution: make the intent explicit in the row handler. Completed rows keep `legIndex: index` (replay; can never advance — correct today). The current row keeps `legIndex: currentIndex`. Future rows must either launch with **no** provenance (`gameHref(game.id)` → standalone, the existing degradation path) or be non-pressable/visually marked as preview-only. Keep `game-host.tsx`'s position copy derived from a validated tuple, and prefer showing "Game N of M" only when the launch tuple matches the durable current leg (otherwise omit the position).
- Implementation considerations: do not "fix" this by forwarding `currentIndex` for future rows — that would let a tap on leg 3 launch leg 3's game as the *current* leg and grant credit at the wrong index (a real skip). Preserve the replay semantics (`advance.test.ts` cases for past legs); each `testID` (`home-workout-game-${game.id}`) and the status node `home-workout-game-status-${game.id}` are automation contracts and must keep their meaning; standalone launches for the catalog are already supported everywhere downstream, so removing provenance from future-row taps is a low-risk degradation.
- Dependencies: Home (`src/app/(tabs)/index.tsx`), route envelope (`routing/route-params.ts` — do not add a launch-time DB check to the route parser; keep the envelope pure), L04-F01 if the recovery pass is added (it must not turn these standalone sessions into tracked legs).
- Risks: changing row tappability is a visible UX change (mitigate: keep completed/current rows tappable); if position copy is omitted for out-of-order launches, TalkBack labels must stay coherent (existing `accessibilityLabel` includes "up next").
- Validation required: (1) new component/integration test under `src/app/__tests__/` (pattern: `home-workout-start.test.tsx`) asserting an "up next" row's push target carries no `workoutKey`/`workoutIndex` (or is disabled); (2) repository-level case in `advance.test.ts`'s "durable ownership-checked advance" block for a future-leg tuple (`legIndex > currentIndex` with matching `gameIds[legIndex]`) asserting `advanced === false` and an unchanged row — the existing coverage (`advance.test.ts:107-116`) is predicate-only and the durable claim is untested; (3) manual/runtime: open Home for a 4-leg instance at index 0, tap leg 4, complete it, then complete legs 1–3 and open the leg-4 session's `/results` — assert the workout does not advance from the mere view.
- Completion criteria: no UI path can produce a launch tuple whose `legIndex !== instance.currentIndex` (or future-row launches are provenance-free and asserted as such); the missing future-leg test exists and passes; the in-game "Game N of M" copy can never disagree with the durable row.

### L04-F03 — `applyReroll` write path is weaker than `advanceForSession`: no `status='active'` in the CAS and no list-shape/bound validation
- Severity: P3
- Confidence: confirmed (code asymmetry); reachability of the degenerate row is `requires runtime validation`
- Category: data-integrity | concurrency | api-contract
- Files: `apps/mobile/src/db/workout.ts:589-598` (`applyReroll` UPDATE + docstring `:540-542`), `apps/mobile/src/db/workout.ts:744-750` (`advanceForSession` UPDATE), `apps/mobile/src/workout/use-workout.ts:200-207` (the only status guard), `apps/mobile/src/workout/templates.ts:92` (`MAX_WORKOUT_GAME_IDS`), `apps/mobile/src/data-portability/deserialize.ts:262` (the only enforcement)
- Evidence:
  - `applyReroll`: `UPDATE workout_instances SET game_ids_json = ?, reroll_attempt = ?, updated_at = ? WHERE date = ? AND reroll_attempt = ? AND current_index = ? AND game_ids_json = ?` — `status` is absent, unlike `advanceForSession`: `... WHERE date = ? AND status = 'active' AND current_index = ? AND updated_at = ? AND reroll_attempt = ? AND seed_version = ? AND game_ids_json = ?`.
  - `applyReroll` docstring: "The total instance length is preserved when `newGameIds.length >= current.gameIds.length`." — a caller contract with no assertion; `merged = [...completedPrefix, ...newGameIds.slice(currentIndex)]` can shrink or grow the stored list arbitrarily, and `status`/`current_index` are never recomputed (so a shrink can leave `status='active'` with `currentIndex === gameIds.length`, i.e. an active workout with no playable leg).
  - `grep -rn "MAX_WORKOUT_GAME_IDS"` → only `templates.ts:92` (definition), `data-portability/deserialize.ts:262` (import validation) and its tests. No repository write path (`getOrCreate`, `applyReroll`, `reconcile`/`persistRepaired`) enforces it, while `advance`/`applyReroll` *do* guard the empty-list case (`db/workout.ts:384`, `:559`).
  - The only `status === 'active'` guard on the reroll path lives in the hook, outside the transaction (`use-workout.ts:200-207`), so it is not re-validated by the CAS.
- Problem: the reroll write trusts its caller for both list shape and lifecycle state. In the one reachable degenerate case (a stored row already at `currentIndex === gameIds.length` with `status='active'` — reachable only through a truncated list, a crafted row, or a future writer), a reroll can be debited for a no-op, and `reconcileActiveInstances` can flip that row to `completed` with an *unchanged* `current_index`, which the reroll CAS predicates (`index`, `reroll_attempt`, `game_ids_json`) would still match — coins spent on a completed workout.
- Why it matters: the workout row is the progression record; two write paths with different invariant strength means the row can be driven into a state (`active` with no playable leg) that only a later `reconcile` load repairs, and the escalation of reroll prices (25/50/75/100) makes a wasted debit user-visible. Practical impact today is low (the live catalog has ~41 eligible games, so the truncation path needs an exhausted pool — `reconcile.ts` documents it as degenerate).
- Root cause: `advanceForSession` was hardened (065/059) with a full CAS + status predicate while `applyReroll` kept the older, narrower predicate; the MAX bound was added for hostile *imports* (`deserialize.ts`) and never pushed down into the repository.
- Recommended solution: extend the `applyReroll` UPDATE to `AND status = 'active'`, and assert the post-merge shape before writing (`merged.length >= 1`, `merged.length <= MAX_WORKOUT_GAME_IDS`, no duplicate ids) — throwing a `WorkoutWriteConflictError`/`Error` rather than persisting a malformed row. Optionally enforce the bound in `getOrCreate` too (cheap `gameIds.slice(0, MAX_WORKOUT_GAME_IDS)` or a throw), so every write path shares the import-level bound.
- Implementation considerations: keep the positional convention and the byte-level predicate (a changed predicate must still be CAS-safe and must not break the non-canonical-JSON leniency documented at `:575-588`); if the merge shrinks the list, recompute `current_index`/`status` in the same statement rather than leaving an unplayable row; do not silently truncate a user's reroll selection to the bound (reject loudly — the caller already sends exactly `remainingSlots` fresh ids).
- Dependencies: L01 (`db/workout.ts` ownership of this file), economy lane for the debit ordering (the debit is already in the same transaction via `paidReroll`, `db/economy.ts:171-198`, which is correct and should not change).
- Risks: an over-strict shape assertion could reject a legitimate `short` (2-game) template reroll — assert against `MAX_WORKOUT_GAME_IDS` (6) and non-empty, never against the length variant; `status='active'` in the predicate must match what `advanceForSession` leaves behind (it sets `'completed'` on the last leg), or every reroll would silently conflict.
- Validation required: `npx jest apps/mobile/src/workout/__tests__/reroll.test.ts apps/mobile/src/workout/__tests__/reroll-partial.test.ts apps/mobile/src/workout/__tests__/lifecycle.test.ts` after the change; new repository test asserting (a) a reroll against a `completed` row conflicts and does not debit, (b) a reroll proposing an over-long/empty list throws and leaves the row untouched, (c) the existing post-completion reroll regression case (`lifecycle.test.ts:256`, `reroll-partial.test.ts:41`) stays green.
- Completion criteria: `applyReroll`'s UPDATE predicates on `status='active'`; a post-merge list that is empty, duplicated, or longer than `MAX_WORKOUT_GAME_IDS` cannot be persisted; no reroll can complete a workout as a side effect of the list rewrite.

### L04-F04 — The workout state machine has no abandon/skip transition; an unwanted current leg can only be escaped with capped, escalating paid rerolls
- Severity: P3
- Confidence: confirmed
- Category: architecture | frontend | docs-dx
- Files: `apps/mobile/src/workout/reroll.ts:29` (`MAX_REROLLS_PER_DAY = 5`) and `:32` (`REROLL_COST_COINS = 25`), `apps/mobile/src/workout/use-workout.ts:200-207` (reroll refuses a non-active row), `apps/mobile/src/components/game-host/game-host.tsx:170-183` (hardware back pauses; only the overlay's Resume/Quit proceeds), `apps/mobile/src/db/workout.ts` (only `getOrCreate` → `advance` → `reconcile` write transitions)
- Evidence: `grep -rn "abandon"` over `src/workout`, `src/app/game/[id].tsx` and `src/components/game-host` returns exactly one hit, a comment (`game-host.tsx:179` "no accidental abandonment (audit B6)"). Quit abandons the leg with no workout-side record: the row stays `active` at the same `currentIndex`. Reroll is the only leg-replacement mechanism and stops at `MAX_REROLLS_PER_DAY` (`rerollCost` 25→100 coins); `useWorkout.reroll` refuses once `rerollAttempt >= 5` or the row is not `status === 'active'`.
- Problem: there is no `skipped`/`abandoned` state, no "skip this leg" affordance, and no way to give up on a day without replaying; the resume pointer can therefore be permanently parked on a leg the user will not play. Within the day this blocks `status === 'completed'` (the workout-completion card and `countCompleted`).
- Why it matters: the daily workout is the primary CTA on Home; a stuck leg degrades it into a dead surface for the rest of the day with no in-product explanation. The constitution's locked reroll economy is not violated (skips are simply not part of it), so this is an honest product/state-machine gap rather than a defect — but it is also *unrecorded*: a future hardening pass will rediscover it.
- Root cause: the daily-workout model treats a day's plan as strictly linear-progress with one exit (`completed`), and reroll was designed as the pressure valve.
- Recommended solution: decide explicitly and document it — either (a) add a bounded `skip` transition (advance the index without credit, recorded in `metadata_json.attempts`/reasons so history is honest and `countCompleted` still requires real play), or (b) document in `docs/PROJECT_CONSTITUTION.md`/DEFERRED_DECISIONS that an unwanted daily leg is intentionally only escapable via the 5-reroll budget, and surface that in Home copy so the user understands the state. Prefer (a) with a per-day skip cap if the product wants completion to remain meaningful.
- Implementation considerations: any skip must be a CAS'd write on the same row shape (reuse `advanceForSession`'s predicate with an explicit reason field) so it cannot be forged through the session-ownership path; `countCompleted()` and history summaries must not count a skipped leg as played (they derive from `currentIndex`/`status` and session rows — a skip must not fabricate a session); the automation contract for `home-workout-game-status-${game.id}` needs a third status label if skips exist.
- Dependencies: `db/workout.ts` (transition + history schema), Home UI, `.agent/DEFERRED_DECISIONS.md` if option (b); interacts with L04-F02 (the same list owns replay/current/future semantics).
- Risks: a skip path is a progression shortcut — cap it and keep it out of XP/rating; adding a state to `status` touches the backup schema, `deserialize` validation and every `status === 'active'` caller (`useWorkout`, `useWorkoutResultAdvance`, `withNavigation`, Home) — a boolean column (`skipped_json`) avoids widening the enum.
- Validation required: if implemented, repository test for `skip` (CAS, idempotent, no session row, no XP), Home test for the new affordance, `npx jest apps/mobile/src/workout apps/mobile/src/app/__tests__/home-workout-start.test.tsx`; if deferred, a documented decision plus a `KNOWN_ISSUES.md`/`DEFERRED_DECISIONS.md` entry.
- Completion criteria: the stuck-leg outcome is either impossible (skip exists, capped, credit-free) or explicitly documented as a deliberate product decision with user-visible copy.

## Checked and found clean
- **Leg advance is exactly-once at the persistence boundary** (check 1). `advanceForSession`'s conditional UPDATE (`db/workout.ts:744-760`) rejects a duplicate/replayed `(key, legIndex, gameId)`: after leg N advances, `current_index` no longer matches, so a relaunch/replay/duplicate result effect reports `advanced: false` and returns the row's fresh state. `advance.test.ts:182` (duplicate after relaunch) and `:207` (durable ownership after process death) cover it. No skip is possible: the ownership predicate requires `instance.gameIds[legIndex] === gameId` **and** `legIndex === currentIndex` (`advance.ts:44-50`), re-checked inside the transaction.
- **Two active instances sharing a game id are routed independently** — `workoutProvenance.instanceKey` is part of the predicate and the update (`advance.test.ts:256`).
- **Standalone/unowned sessions can never claim a leg** — `isWorkoutSessionProvenance` rejects a missing/malformed tuple before any write (`db/workout.ts:718-724`, `advance.test.ts:249`).
- **Substitute-and-preserve (campaign 056) is real in code and well tested** (check 2). Invariant maintained by `reconcileWorkout` (`reconcile.ts:62-172`): played prefix `[0, currentIndex)` byte-identical even when retired; unplayed positions filtered to eligible + first-occurrence dedupe; retired future legs substituted in pool order excluding present ids so length is preserved; `completed` rows byte-identical (index clamp only); `null` when nothing playable remains (caller regenerates via the real seeded selection). Asserted in `reconcile.test.ts` (12 cases: substitution without overfilling, no rewrite of completed history, deterministic re-run, idempotency, input immutability, index clamp past the end) and end-to-end through `session-advance.ts` in `session-advance.test.ts:139` and `lifecycle.test.ts:284/:318`. Degenerate pool exhaustion truncates honestly rather than inventing credit (`reconcile.test.ts:37/:54`, `:170` completes the instance when the index passes the end).
- **A reroll is applied once per attempt and the debit cannot double-apply** (check 3). `paidReroll` (`db/economy.ts:171-198`) does `ledger.getByOperation(operationId)` → balance check → `mutateWorkout(txn)` → `ledger.append(-cost, operationId)` **inside one `db.transaction`**, with `operationId = workout-reroll:${date}:${nextAttempt}`; a retry at the same attempt returns the existing entry without re-applying the mutation, and a CAS conflict (`WorkoutWriteConflictError`) rolls the debit back. The free first reroll takes the non-transactional `applyReroll` branch, which still CASes on `(reroll_attempt, current_index, game_ids_json)`.
- **Reroll protects the played prefix and excludes played games** — `current.gameIds.slice(0, current.currentIndex)` is preserved positionally and passed as `exclude` to `nextWorkoutAfterReroll` (`use-workout.ts:216-247`), with the campaign-011 positional-merge regression documented and covered (`reroll-partial.test.ts:41` for 0–3 completions before reroll, `lifecycle.test.ts:197` for the escalating cost sequence).
- **Rerolled rows are deduped/capped at the hook and the row level** — cap `MAX_REROLLS_PER_DAY = 5` enforced in the UI and re-checked against the live row inside the hook (`use-workout.ts:200-207`), plus a completed-instance refusal (`lifecycle.test.ts:256` asserts no attempt bump and no debit).
- **Resume after force-stop of the *workout position* is correct** (check 4, the parts that are covered): the instance row is persisted at creation and the hook never re-selects on restart (`getOrCreate` is a read when the row exists); `lifecycle.test.ts:167` plays two legs, throws away the hook, and asserts a fresh hook resumes at `currentIndex 2` with the identical `gameIds` and no re-seed; `use-workout-templates.test.ts:118` does the same for a template instance; date rollover preserves each day's partial row and starts the new day fresh (`lifecycle.test.ts:349`, `:412`). Per-leg in-flight gameplay (round state, timers) is deliberately **not** persisted by the workout engine — only the leg boundary is durable; a partially played leg leaves the row untouched at the same `currentIndex` and the leg is simply replayed. That is a defensible design given the daily model, and it is what makes L04-F01 the only real durability gap.
- **Timer/interval cleanup per leg and on unmount** (check 6). The workout host owns no timers; the shared helpers `useGameInterval`/`useGameTimeout` (`src/components/game-host/timers.ts:22-48`) attach `setInterval`/`setTimeout` only while `active` and return the matching `clear*` cleanup, keeping the tick callback in a ref so a changing handler never restarts the interval. Census: only two files under `src/games/**` call `setInterval` directly (`memory-prospective-cue/screen.tsx`, `speed-order-wake` → `speed-order-sweep/components/round-window.tsx`) and both also call `clearInterval`. A "Next Game" launch pushes a new `/game/<otherId>` route (new stack entry, new component instance), so the previous leg's effects unmount and clean up.
- **Back/quit inside a workout leg** (check 6). `GameHost` intercepts Android hardware back (`game-host.tsx:170-183`): an active session is paused, and back is consumed in both states so only the pause overlay's explicit Resume/Quit proceeds; the listener is mounted once via refs and removed on unmount. `game/[id]` is registered with `headerShown: false` (`app/_layout.tsx:282-284`), so there is no header back button to bypass it. (iOS swipe-back gesture behaviour is out of scope/accepted debt.)
- **Route-envelope validation of the launch tuple** — `parseWorkoutLaunchProvenance` (`session-provenance.ts:132`) requires a canonical game id, a canonical instance key (`<YYYY-MM-DD>` or `<date>::<templateId>::<length>`, ≤128 chars) and a bounded safe-integer leg index (`MAX_ROUTE_LEG_INDEX = 5`, `routing/route-params.ts:48`, asserted equal to the templates authority in `routing/__tests__/route-params.test.ts`); malformed params degrade to a standalone launch rather than claiming a leg. `isWorkoutSessionProvenance` re-applies the same bounds to tuples crossing a persistence boundary.
- **Recorded reasons degrade gracefully, by design, after a reroll/reconcile** — `alignedRecordedReasons` (`reasons.ts:126-140`) returns `null` on any length/order drift, `metadata_json` is intentionally not rewritten, and both behaviours are asserted (`history-reasons.test.ts:110`, `use-workout-templates.test.ts:310`). Not a defect.
- **Provenance is dropped from the in-memory map only after the durable commit** — `clearWorkoutSessionLaunch(s.id)` (`db/sessions.ts:566`) runs post-transaction, so a failed persistence still retries with ownership intact (`peekWorkoutSessionLaunch` is non-consuming by design).
- **`getOrCreate` is not a re-seed** — it is an `INSERT … ON CONFLICT DO NOTHING` + read (`db/workout.ts:314-378`), so mounting Home twice in a day cannot replace the day's selection (`lifecycle.test.ts:74`).
- **Test truth for the workout suites (check 7).** 18 suites / ~4,100 LOC under `apps/mobile/src/workout/__tests__/`. Asserted (real behaviour, not smoke calls): ownership predicate matrix incl. wrong game/key/leg, past-leg rejection, repeated-game-id disambiguation (`advance.test.ts`, 21 tests, executed green); durable exactly-once advance + duplicate refusal after relaunch + persisted-ownership reopen (`advance.test.ts:182/:207`, executed green); reconcile substitution/truncation/idempotency/immutability (12 cases, executed green); reroll prefix/positional merge/escalating cost/partial-completion variants (`reroll-partial.test.ts`, `reroll.test.ts`, executed green); selection determinism, per-length counts 2/4/6, exclusion honouring, degenerate catalogs (`catalog-scale.test.ts`, `rotation-templates.test.ts`, `selection.test.ts`, `personalize.test.ts`); whole-lifecycle integration over a real migrated DB + real registry with a mocked clock — create-once, full advance to completion with `countCompleted() === 1`, kill/relaunch resume, reroll cap and completed-refusal, catalog drift repair, date rollover (`lifecycle.test.ts`, `use-workout-templates.test.ts` — inspected, not executed in this lane); reason alignment/drop and metadata round-trip (`history-reasons.test.ts`, `use-workout-templates.test.ts:244/:280/:310`). Merely called (assertion-light): `advance.test.ts:186` calls `findActiveInstanceForSession` and only asserts `not.toBeNull()` before the durable path takes over; the template/history suites mostly assert *shape* (counts, ordering, `null`) rather than invariants of the row after a failure. **Highest-risk untested invariant:** *"a completed session carrying current-leg provenance always ends up advancing that leg exactly once, regardless of process death or write failure between `completeSession` and the advance"* — no test ever completes a session with provenance and then omits/fails the advance (every suite pairs the two in-process: `lifecycle.test.ts:56` `playLeg` asserts `advanced === true`; `advance.test.ts:207` covers repository durability, not recovery), and no test asserts that a future-leg launch from Home now exists. Second highest: the durable claim for a future-leg tuple (see L04-F02 validation item 2).

## Contradictions with existing documentation
- `use-workout.ts` header: "On mount it loads-or-creates today's instance … so the workout survives restart/resume" (module doc). True for the *instance*; the comment in `session-provenance.ts:26-30` ("The in-memory launch map bridges the route and the existing shared game persister") and the module docs of `session-advance.ts` ("Both the in-game results chrome and the `/results` route call this so a workout-launched session advances exactly once at the persistence boundary … duplicate calls, process relaunch and concurrent result surfaces cannot skip or double-advance a leg") together read as if process relaunch is fully covered. The relaunch safety holds only when the session already carries persisted provenance **and** some surface subsequently calls `advanceWorkoutForSession` for it; there is no automatic re-drive after relaunch, which is the gap in L04-F01 (see also `advance.test.ts:207`, whose name — "reopens persisted session ownership before advancing after process death" — asserts repository-level durability, not automatic recovery).
- `reconcile.ts` module doc claims deterministic substitution keeps "the instance length … preserved" (056); `reconcile.test.ts:37` asserts honest **truncation** when the eligible pool has no spare. Both are true (substitution preserves length only while the pool has spares), but the doc sentence overstates the invariant; a reader can reasonably conclude a row is never shortened.
- Home's leg list treats `legIndex: index` as the launch leg for rows it labels "up next" (`(tabs)/index.tsx:862-877`) while the ownership model in `advance.ts`/`session-advance.ts` states that a launch tuple describes the leg the workout *owns*. The UI therefore emits tuples the ownership model must reject (L04-F02).
