# Campaign 051 — Visual DNA Reboot Reference Lock

**Repository:** `quantdale/brain-training`  
**Purpose:** seed research for a major UI overhaul without turning the product into a clone of any one reference  
**Research method:** Refero style-first research, then mobile screen/flow evidence, then visual exploration before implementation

## User problem

The current product is technically mature but visually underwhelming.

The core complaint is not merely “needs polish.” The product feels insufficiently desirable, insufficiently memorable, and too easy to abandon after a short interaction. The redesign must materially improve:

- first-impression appeal;
- visual identity;
- tactile delight;
- game/library desirability;
- perceived quality;
- emotional energy;
- motion/feedback;
- completion/reward satisfaction;
- coherence across Home, Games, Progress, Profile, Rewards, Game Detail, GameHost, and Results.

The new design should be **playful enough to attract younger users, but sophisticated enough not to feel like a preschool app or a Duolingo clone**.

The product should feel like a **pocket cognitive arcade / training console**, not a clinical dashboard and not a generic productivity app.

# Recommended visual thesis

## Working direction: “Cognitive Arcade Console”

The product should feel like a handheld arcade/training console for the brain.

Not:

- clinical;
- productivity SaaS;
- generic card dashboard;
- childish classroom;
- neon cyberpunk for its own sake;
- Duolingo clone.

Instead:

- bold;
- tactile;
- colorful;
- kinetic;
- collectible;
- slightly toy-like in the best industrial-design sense;
- visually confident;
- immediately recognizable;
- delightful in motion;
- highly legible.

### Memorable design move

Treat each game like a **cartridge / poster / arcade title** with a strong visual motif.

Do not generate 42 unrelated illustrations.

Build a scalable system:

- 8 domain visual worlds;
- per-game mechanic signature;
- domain + mechanic combine into a recognizable card/hero treatment;
- selective generated or code-native art;
- consistent art direction.

Games should look worth opening before the user reads the metadata.

# Reference lock

## Primary direction

Playdate-like bold physical/graphic language adapted to a cognitive training app.

## Preserve

1. strong contrast and decisive color blocks;
2. bold typographic hierarchy;
3. tactile, branded controls;
4. content/game imagery treated as a first-class visual object;
5. low reliance on generic shadows/card soup;
6. full-bleed moments mixed with contained functional surfaces;
7. strong, memorable light and dark identities.

## Borrow only

From Duolingo:

- tactile press states;
- completion delight;
- immediate positive feedback.

From Quizlet:

- controlled category accent logic;
- information organization.

From Stryds:

- dark-theme atmosphere;
- energetic abstract motion/motifs.

From Brilliant:

- interaction-first learning screens;
- clear progression.

## Reject

- warm-beige “calm editorial” AI defaults;
- endless rounded white cards;
- gradient-everything;
- random neon everywhere;
- glassmorphism as default;
- every surface using the same radius;
- purple/indigo by default simply because it is fashionable;
- huge hero copy inside ordinary app screens;
- fake 3D blobs with no product role;
- decorative badges everywhere;
- generic dashboard grids;
- copying Duolingo characters or Playdate branding;
- making every domain equally saturated at once;
- turning analytics into arcade noise;
- sacrificing readability for spectacle.

# Visual exploration requirement

Before coding the full overhaul, the agent must produce **three genuinely distinct visual directions** for at least these key surfaces:

1. Home / Today;
2. Games discovery;
3. Game Detail;
4. one active game;
5. Result;
6. Progress overview.

The three directions should not be tiny token variations.

Suggested exploration families:

### Direction A — Cognitive Arcade Console

Bold light/dark color blocks, tactile controls, game-poster identity, graphic typography.

### Direction B — Neon Training Lab

Dark-first immersive atmosphere, restrained luminous motifs, high-tech training energy.

### Direction C — Animated Learning Studio

Bright, expressive, illustration-forward learning energy with stronger playful motion.

Use Refero + image generation if available to make these directions visually concrete.

Then compare them using:

- desirability;
- memorability;
- age range appeal;
- readability;
- accessibility;
- implementation feasibility;
- game identity strength;
- light/dark quality;
- performance cost;
- risk of looking like a clone;
- consistency across Home/Games/Progress/Profile/GameHost.

Choose one dominant direction.

Do **not** average all three into a safe middle.

If the strongest direction materially differs from the working “Cognitive Arcade Console” thesis, document why and update the lock before implementation.

---

# Image generation strategy

Image generation is encouraged when available, but it must change the outcome.

Good uses:

- visual concept boards;
- hero/illustration exploration;
- 8-domain art-direction studies;
- celebratory result artwork;
- background textures/patterns;
- collectible/reward art;
- game-poster studies;
- before/after design mockups.

Avoid:

- generating screenshots and blindly tracing them;
- 42 unrelated one-off images;
- photoreal imagery with no role;
- heavy bitmap dependence for controls;
- inaccessible text baked into images.

Prefer code-native primitives for controls, charts, icons, and core gameplay.

Generated production assets must be optimized, consistently art-directed, and tracked with clear usage.

# Surface-specific north stars

## Home / Today

Should feel like opening a console and seeing **today’s challenge**.

One unmistakable focal action.

Use an expressive training hero or graphic object, not a pile of stat cards.

Secondary context should feel like supporting instruments, not another dashboard.

## Games

Should feel like a **game library/storefront**, not a database.

Users should want to browse.

Game cards need visual identity before metadata.

Suggested Next should feel curated, not algorithmic paperwork.

Browse All should feel rich but fast.

## Game Detail

Should sell the fantasy/mechanic immediately.

Large visual identity.

Short “what you do” explanation.

PLAY is dominant.

Stats/history are secondary.

## GameHost

More immersive.

Chrome recedes.

Mechanic gets the stage.

Feedback feels tactile.

Pause/tutorial are accessible but not constantly dominant.

## Results

Should feel rewarding enough that the user wants another round.

Strong score/performance moment.

Animated or visual celebration bounded by accessibility/reduced-motion.

One obvious next action.

## Progress

Should remain credible and readable.

Do not turn charts into arcade decoration.

Use the new identity in framing, typography, spacing, domain motifs, and selected highlights.

## Profile / Rewards

Profile should feel like the player’s console identity.

Rewards should feel collectible and visually satisfying.

Avoid dense settings-dashboard appearance.

# Implementation principles

- Build or consolidate a real design token system before broad screen edits.
- Create semantic roles, not raw color sprawl.
- Establish typography roles.
- Establish radii by component role.
- Establish tactile states.
- Establish motion tokens and reduced-motion behavior.
- Establish domain/motif system.
- Establish surface hierarchy.
- Establish illustration/asset rules.
- Establish light and dark palettes independently rather than naïve inversion.
- Preserve accessibility from the start.
- Preserve semantic IDs and automation contracts where feasible.
- Do not rewrite backend contracts to fit a visual idea.
- Do not change scoring, persistence, workout identity, schema, economy, or game mechanics unless a real defect is independently found.

---

# Visual QA standard

After implementation, the agent must compare real rendered pixels against the locked direction.

Required:

- before/after screenshots;
- light/dark;
- compact viewport;
- large font scale;
- key states;
- accessibility hierarchy;
- motion/reduced-motion;
- actual emulator interaction;
- design critique pass;
- anti-generic/anti-AI-slop pass.

The implementation is not done because it compiles.

It is done when the current product visibly feels transformed while its protected behavior remains intact.
