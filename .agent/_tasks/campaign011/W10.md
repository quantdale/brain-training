# W10 — Query performance / JSON1 path: differential equivalence + measurement

## Status: COMPLETED (device-leg deferred to W16, see NOT VALIDATED)

## Mission recap
Prove the JSON1 projection paths return byte-equivalent business results vs
the legacy full-row reference, then measure. Result: **equivalence proven at
1k/5k/20k on better-sqlite3 across all three path legs**, after repairing two
independent production defects that had made the entire projection fast path
silently dead since it landed.

## Failure findings (classified)

### F1 — HIGH — JSON1 Progress projection dead-on-arrival (both SQL bugs fixed)
- **Files:** `apps/mobile/src/db/sessions.ts` — `jsonNumberExpr` /
  `coalescedJsonNumbers` (SQL generators behind `PROJECTED_SESSIONS_ALL_SQL`
  / `PROJECTED_SESSIONS_BY_GAME_SQL`).
- **Symptom:** `SessionRepository.listProgressProjection*()` threw on EVERY
  database; `tryLoadProjectedSessionRows` swallowed it and silently fell back
  to legacy full-row reads (`listRecent`). Campaign 010's headline Progress
  optimization therefore had **zero production effect** and its perf contract
  was void while all correctness suites stayed green.
- **Root causes (two independent defects; either alone is fatal):**
  1. *Prepare-time:* single-candidate lists generated `COALESCE(<one expr>)`
     (difficulty `challengeRating`) → SQLite requires ≥2 COALESCE args →
     `SqliteError: wrong number of arguments to function COALESCE()`.
  2. *Run-time:* bare field names interpolated as JSON paths —
     `json_type(raw_result_json,'score')` for score/accuracy/reaction
     candidates (only `$.challengeRating` was prefixed) →
     `SqliteError: bad JSON path: 'score'`.
- **Why undetected:** loaders treat any projection error as "fast path
  unavailable" by design; the convergence suite for projections was pure-JS
  (never executed the SQL); perf probes are opt-in and their absolute deltas
  were attributed to machine noise.
- **Fix:** in `coalescedJsonNumbers`, emit the bare expression when the
  candidate list has length 1 (no COALESCE); in `jsonNumberExpr`, normalize
  bare names to `$.<name>` centrally. No call-site changes; shim/extractor
  contract untouched.
- **Test evidence:** `projections-differential.test.ts` leg-1 gate
  (`expect(fastRows).not.toBeNull()`) red→green; EXPLAIN QUERY PLAN index
  assertions red→green (they prepare the same SQL).

### F2 — LOW (test-infra finding, no product impact)
better-sqlite3's `transaction()` passes its own RAW connection adapter into
the callback, so adapter-level fault injection must re-wrap the
transaction-scoped adapter or the fallback seam bypasses the wrapper.
Documented inside `withBreakers` in the differential suite. Not a product bug.

### F3 — OBSERVATION (recorded only, out of packet scope)
With the session read now cheap, `loadProgressSnapshot`'s residual budget is
dominated by its other members — notably unbounded-ish
`ratings.getHistory(ALL_SESSIONS_LIMIT)` (already flagged as a pushdown
candidate in the `analytics/queries.ts` header). Left untouched.

## Measurement (after equivalence)

Official harness re-run (`node scripts/perf/run-probes.mjs`, baseline
`scripts/perf/baselines/perf-baseline-2026-08-21T21-41-38-715Z.json`) — taken
while ~16 campaign workers loaded the box, so absolute numbers are inflated
(compare with care; e.g. exportLocalData read 5367 ms vs 2069 ms in the
03:17 capture with no code change on that path):

| scenario | 03:17 capture | this run |
|---|---|---|
| loadProgressSnapshot_5000_ms | 39.4 | 69.0 |
| loadProgressSnapshot_20000_ms | 107.2 | 118.6 |
| listRecent_20000_full_rows_ms | 108.1 | 88.6 |

Controlled old-vs-new (PERF_PROBE=1, one process, median of 3, my fixture):

| sessions | legacy listRecent | projection(+mapping) | full snapshot |
|---|---|---|---|
| 1k | 8.0 ms | 5.6 ms | 8.3 ms |
| 5k | 42.9 ms | 23.2 ms | 28.8 ms |
| 20k | 141.4 ms | 83.8 ms | **102.7 ms** |

**Verdict vs 009 baseline (101–107 ms @20k): NO regression.** The repaired
fast path is ~1.6× faster than the legacy session read @20k (~1.9× @5k), and
the end-to-end snapshot now costs less than a bare legacy `listRecent` run in
the same process. End-to-end parity-with-baseline rather than a large win is
expected: the session read is only one member of the snapshot's Promise.all
(F3). A quiet-machine official re-run before final claims is recommended.
