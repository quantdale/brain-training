## Implementation summary

**Landed:** `speed-order-sweep` ("Order Sweep") — a complete production Speed vertical slice at `apps/mobile/src/games/speed-order-sweep/` (17 source files + 2 test files).

**Mechanic:** rapid ordering under time pressure. Every round deals `count` unique number tokens onto a grid, ALL visible at once; the player sweeps them in ascending value order against a draining per-round window. Values are sampled uniquely from 1..maxValue with maxValue ≫ count, so finding each next minimum is a genuine visual-scan/compare task rather than counting up. Perfect rounds (full sweep, zero wrong taps) shrink the next window; wrong taps break the streak but leave the board intact; expiry forfeits the remaining tokens.

**Distinctness rationale:**
- vs `speed-tap-rush`: Tap Rush spawns ONE target at a time at unknown positions (reaction + aiming); Order Sweep shows every target simultaneously — the challenge is serial ordering/scanning among many visible options, not single-target reaction.
- vs `speed-quick-compare`: Quick Compare is a two-stimulus comparative judgment per round; Order Sweep has no pairwise judgment at all.
- vs `speed-reaction-time`: Reaction Time measures simple RT to a GO signal with false-start penalties; Order Sweep has no waiting signal and no false starts.
- vs `speed-color-match`: Color Match is a Stroop-style stimulus→response mapping conflict; Order Sweep has no mapping conflict — the semantic content is numeric order.
- vs W01 `attention-sustained-vigilance` (go/no-go SART): no go/no-go dimension, no rare-target stream, no sustained vigilance — every token is a target; the demand is ordering/scanning speed under countdown.
- Bonus contrast vs `memory-running-order` (Memory domain): that game hides the sequence and tests recall from memory; Order Sweep keeps everything visible — zero memory load by construction.

**Key files:** `game.json`, `game-definition.ts`, `types.ts`, `difficulty.ts` (named levels + adaptive window band [4000,10000] ms around neutral 8000 ms → rating 0.5), `generator.ts` (per-round/per-attempt RNG forks; partial Fisher–Yates value sampling; shuffled cell deal; re-draw policy rejecting trivially row-major-sorted boards; `validateRound` invariants), `reducer.ts` (pure state machine; pause/resume shifts ALL open time anchors — deadline, round start, last-clear — by one delta so gaps never include pause time), `scoring.ts` (documented formula: pace = window/count; 100 pts + up-to-50 speed bonus per clear; 40/token perfect bonus; normalize = 0.6·clearRatio + 0.4·meanSpeed), `session.ts` (diagnostic metadata + dbSessionPersister seam + FNV-1a seedToNumber), `hooks.ts` (assertDevOnly QA hooks + tutorial lifecycle), `screen.tsx` (SessionLifecycle, AppState auto-pause, finalizedRef double-submit guard, opaque pause hiding the board from the accessibility tree, dev-gated QaPanel), `components/` (token-grid, round-window bar, tutorial with interactive demo board, thin delegates to shared GameButton/PauseOverlay/QaPanelShell), `versions.ts`, `index.ts`.

**Design decisions:** token testIDs are value-addressed (`speed-order-sweep.token.<value>`) for stable QA targeting; cleared tokens stay visible but disabled so the sweep path remains readable; sensory uses only canonical feedback events ('correct'/'wrong'/'success'/'failure'); per-tap feedback fires in the tap handler while round-level stings key on `(roundOutcome, roundIndex)` so consecutive same-outcome rounds still play.

**Validation performed:** ONE `npx tsc --noEmit` run from apps/mobile — zero errors under `src/games/speed-order-sweep/**` (9 reported errors are mid-edit syntax breakage in W13's `src/app/data-management.tsx` and W06's `src/db/workout.ts`; not my surfaces).
