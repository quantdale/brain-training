## Implementation summary

**Compatibility freeze (verified before editing):** every existing export/method of
`adapter.ts`, `sessions.ts`, `profile.ts`, `rating.ts`, `favorites.ts`,
`tutorial.ts`, `types.ts`, `index.ts` kept byte-compatible (additive only). The
`SQLiteAdapter` interface was deliberately NOT extended — several CI guard tests
(`perf-db-query-patterns.test.ts`, `offline-boundary.test.ts`) construct inline
object literals of it, so any new required member would break files owned by
other workers. All new capability ships as free functions + repository methods.

**What landed:**

1. `db/query.ts` (NEW) — pure, DB-free query-building helpers:
   `SQL_VARIABLE_CHUNK` (500), `DEFAULT_READ_LIMIT` (50), `MAX_READ_LIMIT`
   (10 000), `chunk()`, `buildInPlaceholders()`, `clampLimit()`,
   `normalizeOffset()`, `joinAnd()`, `requireFiniteNumber()`. No caller text is
   ever interpolated into SQL; values always bind as `?` params.
2. `db/batch.ts` (NEW) — `executeBatch(adapter, statements)`: runs a list of
   parameterized write statements inside ONE transaction (all-or-nothing,
   rolls back on first failure, empty batch short-circuits). Generic primitive
   for future bulk import paths.
3. `db/sessions.ts` (additive) — projection/pagination/aggregate/bulk APIs on
   `SessionRepository`:
   - `SessionSummary` DTO (`id, gameId, xp, normalizedResult, durationMs,
     completedAt`) — exactly the columns the 009 audit said Progress screens
     need, never the JSON blobs.
   - `listSummaries(query)` — column-limited reads with gameIds/from/to/
     min/max filters, asc/desc order, limit+offset paging.
   - `pageSummaries(cursor?, limit)` — keyset pagination (`completed_at DESC,
     id DESC`) with expanded OR keyset predicate; fetches limit+1 so `hasMore`
     needs no COUNT scan.
   - `countSessions(filter)` and `getSessionWindowAggregate(filter)` —
     COUNT/SUM/AVG/MAX/MIN pushdown in one statement.
   - `getDailySessionCounts({dayBoundary})` — one row per active day pushed
     down to SQLite; `'utc'` matches the analytics calendar convention,
     `'local'` matches the streak engine's local-calendar convention.
   - `listByIds(ids)` — bulk read preserving caller order, chunked IN lists.
   - Shared `buildSessionFilter()` composes the WHERE clause once for all of
     the above; gameIds dedupe + OR-group under the variable budget.
4. `db/rating.ts` (additive) — `getHistoryWindowed({domain, fromMs, toMs,
   limit, offset})`: bounds the unbounded `getHistory(ALL)` pattern flagged by
   the 009 audit. Also refactored the two existing history SELECTs onto a
   shared `HISTORY_COLUMNS` constant (same output columns, zero behavior
   change).
5. `db/favorites.ts` (additive) — `FavoriteEntry`, `listFavorites()` (full
   rows), `setFavorites(ids)` (batch, single transaction + single clock
   capture), `areFavorites(ids)` (bulk membership check, chunked IN).
6. **SCHEMA CHANGE v9 (documented use of the packet exception):**
   `SCHEMA_VERSION` 8 → 9; migration v9 adds only
   `CREATE INDEX IF NOT EXISTS idx_rating_history_created_at ON rating_history
   (created_at)` (`SQL.createRatingHistoryCreatedAtIndex`). Append-only,
   collision-safe, no table/column/row changes; mirrors v8's completed_at
   lesson and makes the unfiltered windowed history read index-backed instead
   of scan+sort. Verified safe against consumers: backup `schemaVersion` is
   informational only (data-portability types + adversarial tests accept old
   values); migration tests iterate dynamically off `SCHEMA_VERSION` and assert
   `MIGRATIONS.length === SCHEMA_VERSION` (9 = 9 holds).
7. `db/index.ts` (additive re-exports only) — new helpers, `executeBatch`,
   `isValidSessionCursor`, and all new types. No existing export removed or
   renamed; verified no `export *` consumers exist that could collide.
8. `db/__tests__/query-helpers.test.ts` (NEW, 8 pure tests, no DB) — pins
   chunk splitting/validation, placeholder building, limit/offset
   normalization, joinAnd, requireFiniteNumber, cursor validation, and both
   executeBatch short-circuit paths.

**Design decisions:** keyset pagination uses the expanded `(a < ? OR (a = ?
AND b < ?))` form rather than SQLite row-values for maximum portability across
whatever SQLite builds expo-sqlite/better-sqlite3 ship; all new list APIs
tie-break ordering on `id` so equal timestamps paginate deterministically;
read limits are hard-clamped at `MAX_READ_LIMIT = 10_000` so the new APIs
cannot regress into the unbounded-materialization pattern the audit flagged;
per-API index usage is documented in each method's JSDoc
(`idx_game_sessions_completed_at`, `idx_game_sessions_game_id`,
`idx_rating_history_domain`, `idx_rating_history_created_at`).

**Validation:** ONE `npx tsc --noEmit` run from apps/mobile near completion:
zero errors in any file I own. The run reported 3 pre-existing/concurrent
errors in surfaces I do not own (`components/a11y/dialog.tsx` W14,
`games/speed-order-sweep/scoring.ts` W02, `quests/history.ts` W12) — left
untouched per contract.
