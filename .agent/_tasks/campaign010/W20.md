## Implementation summary

New module `apps/mobile/src/sync/` — pure typing + deterministic pure functions, zero dependencies, zero network, zero db writes, nothing wired into screens:

- **`types.ts`** — DTO convention: `SyncDto { id, updatedAt, deleted }` (tombstone convention documented on the type), optional `SyncProvenance` (`originDeviceId`, `dtoVersion`), `SYNC_DTO_VERSION = 1`. Frozen table inventory `SYNC_TABLE_DESCRIPTORS`: all 11 authoritative local tables (mirrors `db/schema.ts`; app-shipped `quests`/`achievements` definition tables deliberately excluded as non-player-authored). Each descriptor carries its `SyncMergeClass` (`last-write-wins` | `field-merge` | `append-only`) and, for AUTOINCREMENT-PK append-only tables (`currency_ledger`, `rating_history`, `xp_awards`), the `naturalKey` future merges dedupe on (`operation_id`, `(session_id, domain)`, `(source, reason, created_at)`). Derived-table flag marks rating_history as reconstructable from activity history (constitution §6). Lookup helper `syncTableDescriptor()` throws on unknown names.
- **`change-log.ts`** — per-table change-log seam: `ChangeLogEntry { seq, table, rowId, op: 'upsert'|'delete', changedAt }`, `ChangeLogCursor`, synchronous `ChangeTracker` interface (recording must never make gameplay wait), `createInMemoryChangeTracker(clock?)` reference implementation (monotonic gap-free seqs, injectable clock), and pure `coalesceByRow()` reducing entries to latest-per-row with deterministic `(table, rowId)` ordering for byte-stable push batches.
- **`conflict.ts`** — policy descriptors + pure resolvers. `resolveLastWriteWins()`: later `updatedAt` wins, exact ties broken by lexicographically greater `id` so both devices converge identically regardless of argument order. `FieldMergeDescriptor<T>` maps field names to rules (`last-write-wins` | `max` | `min` | `sum`) with checked keys; `resolveFieldMerge()` applies them ("preserve valid bests" via max), falls back to row-LWW for non-numeric values under numeric rules, short-circuits to whole-row LWW when either side is a tombstone, and returns per-field `FieldResolution[]` diagnostics. Merged `updatedAt` = max of inputs so merged records never sort before their sources.
- **`engine.ts`** — `SyncEngine` interface skeleton (`backendId`, idempotent `push(deviceId, changes, nowMs)`, cursor-paginated `pull(cursor)`) plus result types (`SyncPushResult`, `SyncPullResult`, `RemoteChange`, `SyncRejection`, `SyncStatus`). Contract notes frozen in header: engines return data, callers resolve via conflict policies and apply transactionally. `createNoopSyncEngine()` accepts everything / pulls nothing — deterministic, offline, lets call sites be written against the seam today.
- **`index.ts`** — public entry point; header documents the naming distinction from unrelated `progression/sync.ts` (quest re-evaluation).
- **`__tests__/sync-seams.test.ts`** — 5 describe blocks / 7 tests (within the ≤8 cap): LWW ordering + symmetric tie-break, field-merge max/lww behavior, tombstone short-circuit, tracker seq/clock semantics, coalesce ordering, no-op engine contract, descriptor completeness + natural-key presence.

### Session-identity verification (read-only, task 2)

`components/game-host/session-identity.ts` (wave 1, debt D1) — VERIFIED collision-safe for local use:
- Format `<gameId>-<time36>-<counter36>-<random6>`; the process-wide monotonic counter makes same-millisecond sessions unique within a run (fast QA restart loops are safe).
- Across restarts the counter resets, but the advancing wall-clock bucket plus ~36^6 ≈ 2.2e9 random suffix space keeps collision probability negligible.
- Caveats (documented, acceptable): uses `Math.random()` (non-crypto) and `Date.now()` (wall clock — fine for identity, not timing); ids are NOT guaranteed globally unique across devices (would require same gameId + same ms + same counter + same random suffix).
- Conclusion: adequate as local identity exactly as-is. No migration needed now; global uniqueness should come from device-instance-id namespacing at sync-export time (below), not from rewriting identity columns. No action required by parent.

### Device-instance-id migration report (report-only, task 3 — NOT implemented)

What a future migration would entail (schema work is out of scope here):
1. **Identity source**: one durable UUID per install (`crypto.randomUUID()` with a Hermes-safe fallback or `expo-crypto`), stored outside the row set (e.g. profile settings or a singleton table) so it survives wipes-by-restore decisions.
2. **Schema v10 (additive)**: e.g. `origin_device_id TEXT` on syncable mutable tables + optional device registry table; backfill existing rows with the local instance id (claims pre-existing single-device history). Backfills on append-only tables require the drop-trigger/backfill/recreate-trigger-in-one-transaction pattern proven by migration v8.
3. **Integer PKs stay local**: `currency_ledger.id` / `rating_history.id` / `xp_awards.id` (AUTOINCREMENT) can never be globally unique — cross-device identity must use the natural keys already declared in `SYNC_TABLE_DESCRIPTORS`.
4. **Session ids**: `game_sessions.id` is TEXT and collision-safe locally; namespace/prefix with the device instance id at export time rather than rewriting rows.
5. **Ripple effects**: backup envelope gains optional origin fields (additive version bump, backward compatible); conflict policies above consume `originDeviceId` unchanged.
6. **Timing**: cheap while the catalog/user base is small (D3's original rationale); effort small-medium, risk low if kept additive.
